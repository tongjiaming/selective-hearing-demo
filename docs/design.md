# 方案与边界

原始方案日期：2026-10-10。下文区分用户需求与建议实现。2026-10-13 已开始开发，当前采用的不同后端与实测范围见 [实现与实测](implementation.md)；此文中的建议不代表已实现。

## 1. 要解决的问题

A、B 在用户附近交谈，允许同时说话。用户戴 AirPods Pro，通过 Windows 上的按钮选择主要听到谁。

选择后播放的是从混合收音中提取的目标人声音频，不是转写后再合成。不能用分别采集的干净音轨调音量，冒充混合语音分离；也不能仅在轮流讲话时静音，冒充重叠语音分离。

## 2. 已确定的设备分工

```text
AirPods Pro 麦克风
    ↓ 蓝牙输入
Windows PC
    ├─ 持续收音和音频缓冲
    ├─ 说话人发现与身份维护 → 动态按钮
    ├─ 参考声音采集 → 目标说话人提取
    └─ 输出选择与时间对齐
    ↓ 蓝牙输出
AirPods Pro 播放
```

用户已提出去掉 iPhone，改为耳机与 Windows PC 直连。iPhone App、Wi-Fi 音频桥接、Mac 编译均不属于当前最小链路。

优先使用 AirPods 麦克风，不能默认替换成手机或 PC 麦克风。其他麦克风仅在 AirPods 环境拾音不满足要求时作为对照实验或后续备选。

## 3. 自动发现与按钮

用户明确希望：听到新的人的声音后，自动识别并添加一个按钮。

建议交互：

- 起始显示“全部听”“全部静音”。
- 检测到新人后显示“正在识别新说话人”。
- 身份与参考样本达到可用条件后，显示“说话人 1”“说话人 2”等按钮。
- 同一个人再次讲话，复用其按钮并显示正在讲话。
- “识别”表示区分同一个人与不同人，不代表知道真实姓名。

以上等待状态、改名、正在讲话提示属于建议交互，尚未实现。

建议新人默认开启；全部静音期间出现的新人也保持静音。这个默认策略尚未由用户单独确认。

最小质量验证先限制为两人。动态新增按钮是已纳入的需求，但超过两人的同时提取、任意多人组合播放和容量上限尚未确定。

## 4. 从认人到只听某人

diart 等说话人识别模型提供“哪个时间段属于哪个说话人”。这些标签本身不是分离后的音轨，也不一定是提取模型可以直接使用的声纹向量。

建议采用自动采集参考声音的连接方式：

1. 持续维护本次会话的说话人身份。
2. 找到某人单独讲话、质量较好的时间片段。
3. 按时间戳从原始收音缓冲中截取片段，作为该人的参考声音。
4. 将按钮绑定到应用内身份及其参考声音。
5. 选中该人后，将当前混合音频和该人的参考声音送入目标说话人提取模型。
6. 将提取结果播放到耳机。

```text
当前混合收音（A+B） + A 的参考声音 → 提取模型 → A 的声音估计
当前混合收音（A+B） + B 的参考声音 → 提取模型 → B 的声音估计
```

这可以减少专门的登记动作，但不是无需声音样本。新人第一次出现就持续与别人重叠讲话时，可靠参考样本可能无法立即获得；不能承诺即时发现并可控。

## 5. 最小输出状态

| 选择 | 软件播放内容 |
| --- | --- |
| 只听 A | 目标为 A 的提取音频 |
| 只听 B | 目标为 B 的提取音频 |
| AB 都听 | 原始混合收音 |
| 都不听 | 不播放，仍收音并维护必要状态 |

原始路径和模型路径可能有不同延迟。切换时需要管理时间戳、缓冲、模型状态及播放边界，避免重复、跳过音节、爆音或延迟不断累积。具体策略待实测后确定。

## 6. 物理与技术边界

- 软件静音只关闭数字播放；外界声音仍可能直接漏入耳朵。用户已接受一定漏音。
- ANC 和耳塞隔音不等于完全阻断周围人声。
- 普通蓝牙输入不等于能读取 AirPods 通透模式的原始双耳麦克风阵列。
- Windows 经典蓝牙同时收音和播放使用 HFP；实际采样率、处理方式、音质和延迟必须在设备上确认。
- 需要先证明附近 A、B 的声音都能进入 AirPods 输入。不能预先断言它一定适用或一定不适用。
- 说话人身份可能认错、重复建人或发生漂移；模型输出可能残留其他人声。
- 流式识别的输入等待时间、模型计算耗时和耳机端到端延迟是不同指标。
- 能识别多个说话人，不等于能同时输出这些人的独立音轨。

## 7. 暂不纳入

关键词例外放行、叫用户名时自动放行、语音助手、转写界面、手机端推理、量产级降噪效果，以及模型训练。

优先复用预训练模型，先完成可演示且可测量的最小链路。
